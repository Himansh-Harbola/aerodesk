# AeroDesk Architecture and Tradeoffs

## Architecture

AeroDesk is a Next.js App Router application backed by Supabase.

- **Frontend**: Next.js App Router, React, TypeScript, Tailwind CSS.
- **Backend/API**: Supabase Postgres, Supabase Auth, Supabase Realtime, and RPC functions.
- **State**: Zustand stores with `persist`.
- **PWA**: `next-pwa`, manifest, generated service worker, offline fallback, install prompt.

## Core Flow

1. Users search flights by origin, destination, date, and passenger count.
2. Server Components load matching flights through the Supabase server client.
3. Users select a flight and choose a seat from the cabin map.
4. Seat selection is optimistic in Zustand.
5. Booking confirmation calls the `reserve_seat` RPC.
6. The RPC locks the seat row, rejects occupied seats, inserts the booking, inserts passenger data, and marks the seat unavailable.
7. Users manage bookings from My Bookings.
8. Cancellation calls `cancel_booking`, which updates booking status and frees the seat atomically.
9. Rescheduling calls `reschedule_booking`, which validates same-route flights, moves the seat, records the reschedule, and charges the fare difference.

## Database Design

Required tables:

- `flights`
- `seats`
- `bookings`
- `passengers`
- `reschedules`

RLS is enabled on every table. Flights and seats are public read models. Booking-related rows are user-scoped through `auth.uid()`.

## RPCs

- `reserve_seat`: prevents double booking with `FOR UPDATE`.
- `cancel_booking`: cancels and frees the seat in one transaction.
- `reschedule_booking`: supports same-route rescheduling, seat movement, fallback seat assignment, and fare-difference charging.

## Realtime

The seat map subscribes to Supabase Realtime updates on the `seats` table for the selected flight. When another user books a seat, availability updates without a refresh.

## Zustand Stores

- `useFlightStore`: search query, selected flight, selected seat, booking step, and passenger form data.
- `useUserStore`: session token and cached bookings.

`partialize` excludes passport numbers from persisted state. Booking reset runs after completion/cancellation and logout.

## PWA

The app includes:

- Manifest with name, short name, theme color, standalone display, and 192/512 icons.
- Service worker generated by `next-pwa`.
- Explicit service-worker registration fallback.
- Offline page.
- Install prompt banner.
- Cached booking display using last known browser data.

## Tradeoffs

- Supabase Auth test users are documented instead of seeded directly through public SQL because Auth users are normally created through the Auth dashboard/admin API.
- The generated six-month route network creates many seat rows. This makes search/reschedule realistic, but it is heavier than a minimal seed.
- Search results are capped and paginated so broad searches do not render thousands of cards.
- Rescheduling picks a new flight and automatically assigns the same seat number when possible. If unavailable, it falls back to another available same-class seat, then any available seat. A full seat-picker during reschedule would be a future enhancement.
- Chrome 148 no longer exposes a separate Lighthouse PWA score in the same way older Lighthouse versions did, so the README includes manifest, service worker, installability, and Lighthouse evidence screenshots.
- Offline My Bookings uses browser-local cached booking data separate from the persisted Zustand auth store, keeping the assignment requirement that only the session token is persisted in the user store.

## Future Improvements

- Airport autocomplete backed by a dedicated airports table.
- Admin dashboard for flight/seat inventory.
- Automated Playwright tests for booking, cancellation, and reschedule flows.
- Server-side pagination for very large flight searches.
- Reschedule-specific seat picker.
